# Brainstorming & Process Summary

The system turns a spoken description into a working application through six agents that each handle one stage of the process: a Scope Gate, a Project Manager, a Requirements Analyst, an Architect, a Developer, and a Code Reviewer, followed by an automated Testing stage. The pipeline was mapped out the way a real software team would divide the work — one role, one decision, per stage — so each stage can focus entirely on its own judgment and the result can be checked and refined before it's final, rather than depending on a single generation pass to get everything right at once. Each stage passes its output to the next, and the Developer's result is verified and refined for up to three passes before the final application is produced — a single, self-contained file that runs immediately in a browser, with no server or build step required.

The Scope Gate runs first, before any other stage. It reads the transcript and makes one decision: does it describe an actual goal or idea for an application? Keeping that judgment as its own dedicated first step, rather than folding it into another stage, means it gets the model's full attention and means every later stage's effort goes only toward a genuine request. When it does find a real goal, the pipeline continues to requirements extraction and build; when the recording doesn't describe anything to build, the person is told so directly.

Testing is carried out by actually running the generated application in a real browser, on the reasoning that an application's correctness should be judged by how it behaves when run — the same standard a real QA process would apply — rather than by a language model reviewing code it just wrote. Depending on what the application needs, the test drives it through the relevant flow: registering and logging in a user for apps with accounts, or adding, editing, filtering, and deleting a record for apps that manage data, confirming each step produces the expected result on screen. This is what the three-pass build cycle checks against to arrive at a working, executable result.

Development was done using Claude Code as the primary AI tool, chosen for its ability to iterate directly against real, running output: each stage's prompt was refined by testing it against generated results and observing the outcome, rather than designing it once from theory. The model backend runs on free-tier language models through OpenRouter, behind one swappable provider interface — a deliberate choice to keep the system accessible and flexible rather than tied to a single vendor. Transcription runs on Groq's hosted Whisper API, chosen for a reliable, ready-to-use speech-to-text step without adding local model management to the system.

The result is a complete, working pipeline: a recording goes in, and a functioning, ready-to-run application comes out.
